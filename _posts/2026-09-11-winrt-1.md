## An Ugly History

I first began looking at cpp/winrt back before WinUI3 was a thing, or was very new. At that time, MS was pushing MSIX packaging with full certificate signing requirements. The certificate cost alone drove me away from that! Eventually they recognized the need to support free-standing, unsigned deployments (using a third-party installer - basically the decades old installation method). Unfortunately, just getting an unpackaged project set up in Visual Studio was a real pain and had all kinds of weird requirements in the project file.

Straight winrt library calls were fine - MS provided a nice and simple command line example. It was really the move to XAML window/component/layout definition that was really broken and once you actually wanted to have a GUI, you had to deal with XAML! MS had no visual XAML designer for cpp/winrt projects. You could either create your GUI programmatically, using calls to the XAML related functions through winrt, or you could hand write XAML and set up the XAML binding. It was a real mess.

## cpp/winrt Today

Fast forward to 2026, and we're still kind of in the same place. The recommended workflow for getting an unpackaged Visual Studio project up and running is to create a *packaged* project, then *manually* edit the project file and set the `<WindowsPackageType>` attribute to `none`. There is still no visual XAML editor. *claude* recommended going so far as to spin up a separate .net project and use the visual XAML editor *there* to generate the XAML code. Really!? There is a WinUI sample site that gives the XAML for each element, so I guess handwriting XAML is just something I'll have to get used to. 

Because cpp and XAML live in separate worlds, you have to `bind` data objects and create a pathway for the displayed data object in XAML to process updates to and from the underlying cpp code. This requires a pretty complicated workflow of defining the data object in `midl` - a c-like definition language used just to describe data layout for passing between ABIs like XAML and cpp. There's a separate midl compiler that converts this into object code and then XAML and winrt (through a cpp projection) can understand how to read and write to this data object, passing it around using windows COM under the covers. 

As a result of all this, we have a wonky project setup, we have a tedious and error-prone manual XAML requirement, we have an additional midl data layer that has to be created for all custom data passed from cpp to the UI via XAML, and we have a ton of hand-written boilerplate language to do all that. I wish MS had spent the effort to automate all that boilerplate cpp, midl, and XAML code but we will find ourselves doing it manually. I look at is as a learning experience. At least I'll understand how all this works "under the covers". If you thought learning COM was a challenge, how about re-implementing an entire midl abstraction layer on TOP of COM!
