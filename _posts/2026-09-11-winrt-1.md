## An Ugly History

I began writing Windows applications using standard the good old Win32 api. I loved how small the compiled applications were, how fast the UI elements were. It was really quite amazing that all these years after the initial releases of windows, Win32 still worked and worked amazingly well. Unfortunately, with Win32, you're limited to the old-fashioned, built-in UI components. Things like the File Picker were stuck in old Win95 looking controls. Which is really perfectly ok, but looks outdated when compared to Windows 10/11 and some of their components. To get these shiny new components, Microsoft wanted me to move over to WinUI and that means switching to XAML to define my UI layout.

I first began looking at cpp/winrt and WinUI back before WinUI3 was a thing, or was very new. At that time, MS was pushing MSIX packaging with full certificate signing requirements. The certificate cost alone drove me away from that! Eventually they recognized the need to support free-standing, unsigned deployments (using a third-party installer - basically the decades old installation method). Unfortunately, just getting an unpackaged project set up in Visual Studio was a real pain and had all kinds of weird requirements in the project file.

Straight winrt library calls were fine - MS provided a nice and simple command line example. It was really the move to XAML window/component/layout definition that was really broken and once you actually wanted to have a GUI, you had to deal with XAML! MS had no visual XAML designer for cpp/winrt projects. You could either create your GUI programmatically, using calls to the XAML related functions through winrt, or you could hand write XAML and set up the XAML binding. It was a real mess.

## cpp/winrt Today

Fast forward to 2026, and we're still kind of in the same place. The recommended workflow for getting an unpackaged Visual Studio project up and running is to create a *packaged* project, then *manually* edit the project file. There is still no visual XAML editor. *Claude* recommended going so far as to spin up a separate .net project and use the visual XAML editor *there* to generate the XAML code. Really?? There is a WinUI sample site that gives the XAML for each element, so I guess handwriting XAML is just something I'll have to get used to. 

Because cpp and XAML live in separate worlds, you have to `bind` data objects and create a pathway for the displayed data object in XAML to process updates to and from the underlying cpp code. This requires a pretty complicated workflow of defining the data object in `midl` - a c-like definition language used just to describe data layout for passing between ABIs like XAML and cpp. There's a separate midl compiler that converts this into object code and then XAML and winrt (through a cpp projection) can understand how to read and write to this data object, passing it around using windows COM under the covers. 

As a result of all this, we have a wonky project setup, we have a tedious and error-prone manual XAML requirement, we have an additional midl data layer that has to be created for all custom data passed from cpp to the UI via XAML, and we have a ton of hand-written boilerplate language to do all that. I wish MS had spent the effort to automate all that boilerplate cpp, midl, and XAML code but we will find ourselves doing it manually. I look at is as a learning experience. At least I'll understand how all this works "under the covers".

Microsoft has also moved their product naming around. They've switched from "Universal Windows Platform" to Windows Runtime and Windows App SDK. So you have to be careful when you're looking for docs. WinRT is the Windows Runtime. Cpp/WinRT is the C++ projection of the WinRT. WinUI3 is (currently) the most recent collection of "Fluent" UI elements and requires a UI defined in XAML. Windows App SDK is an SDK for the Windows Runtime (I guess?) and I think has to be used to get access to WinUI3. I've found the MS docs for WinUI3 Application Development to be helpful, but they're incomplete with regard to unpackaged apps. 

## Project Setup

I'll be working in Visual Studio 2022. The official MS docs can be found here: [Microsoft cpp/winrt Documentation](https://learn.microsoft.com/en-us/windows/apps/develop/cpp-winrt/intro-to-using-cpp-with-winrt) and [Microsoft WinUI App Documentation](https://learn.microsoft.com/en-us/windows/apps/get-started/start-here?tabs=visual-studio) Unfortunately, as of this date, MS cpp/winrt docs still refer to a *Universal Windows Platform Development* Visual Studio workload, even though this no longer exists ([Github Issue Filed](https://github.com/MicrosoftDocs/windows-dev-docs/issues/6121)). I just install "Desktop development with C++" and "WinUI application development" with the C++ Winui tools optional feature. You also have to enable developer mode on your PC if you want to allow unsigned packaged apps to be installed. See MS docs above.

### 1. Create New Project

Select or search for the **"WinUI Blank App (Packaged)"** project template and give it a project name. I used `WinUIApp`.

![WinUI Blank App (Packaged)](/assets/images/2026-09-11-winrt-1/winui-project-template.png)

After creating your new project, you may want to try and compile and run it, just to make sure it works. 

![WinUI Default App](/assets/images/2026-09-11-winrt-1/winui-default-app.png)

Beware though, as a *packaged app*, it will install itself into Windows automatically! You can search for it on the Start menu and right click to uninstall it after testing that it works.

![WinUI Uninstall](/assets/images/2026-09-11-winrt-1/winui-uninstall.png)

### 2. Manually Update Project File

I don't want to use Microsoft's MSIX packaging. It requires a signing certificate and I don't want to buy one. Last time I tried, you couldn't use a self-signed one either. So we need to change this project to an "Unpackaged" app which will make a free standing .exe (possibly with some additional .dlls) that we can just install like normal. The documentation for running a WinUI3 app unpackaged are here: [Distribute an unpackaged WinUI 3 app](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/unpackage-winui-app?tabs=cpp)

Right click your project in the Solution Explorer and select **"Unload Project"**. That should bring up the project file XML in the editor (if not, right click the unloaded project in Solution Explorer and select "Edit Project File". Either edit or add the following tags, somewhere in the `<PropertyGroup Label="Globals">` section: 

```
<WindowsPackageType>None</WindowsPackageType>
<AppxPackage>False</AppxPackage>
```

Right click your unloaded project in the Solution Explorer and select "Reload Project". Re-Build and run your project.

### 3. Fix Problems

If you're like me, you'll get an exception as soon as your run the test app. This is related to the XAML Live Preview window. Somehow, the unpackaged version of the app causes the XAML Live Preview window to call something the app doesn't know how to handle and causes a couple unhandled exceptions to be thrown. Pressing the debugger Continue button a couple times should get you past them and you should see your app running.

To fix this, you have two options (choose one):
1. Disable XAML Hot Reload for WinUI apps in your Visual Studio debugging settings
   
   ![Disable WinUI XAML Hot Reload](/assets/images/2026-09-11-winrt-1/disable-winui-hot-reload.png)
2. Ignore winrt::hresult_error exceptions
   
   ![Disable Exception Type](/assets/images/2026-09-11-winrt-1/disable-exception-type.png)
