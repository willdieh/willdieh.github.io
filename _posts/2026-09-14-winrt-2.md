## Project Layout

Let's take a look at the project layout created by the WebUI template

![WinUI Project Layout](/assets/images/2026-09-14-winrt-2/winui-project-layout.png)

### app.manifest

At the top you'll see the app.manifest. This file will be included along with our .exe to tell windows how to load the application. It allows us to specify several interesting Windows specific configuration settings such as minimum Windows version. We'll just leave it alone for the most part. [Microsoft Documentation here](https://learn.microsoft.com/en-us/windows/win32/sbscs/application-manifests)

**`app.manifest`**
```xml
<?xml version="1.0" encoding="utf-8"?>
<assembly manifestVersion="1.0" xmlns="urn:schemas-microsoft-com:asm.v1">
  <assemblyIdentity version="1.0.0.0" name="WinUIApp.app"/>

  <compatibility xmlns="urn:schemas-microsoft-com:compatibility.v1">
    <application>
      <!-- The ID below informs the system that this application is compatible with OS features first introduced in Windows 10. 
      It is necessary to support features in unpackaged applications, for example the custom titlebar implementation.
      For more info see https://docs.microsoft.com/windows/apps/windows-app-sdk/use-windows-app-sdk-run-time#declare-os-compatibility-in-your-application-manifest -->
      <supportedOS Id="{8e0f7a12-bfb3-4fe8-b9a5-48fd50a15a9a}" />
    </application>
  </compatibility>
  
  <application xmlns="urn:schemas-microsoft-com:asm.v3">
    <windowsSettings>
      <dpiAwareness xmlns="http://schemas.microsoft.com/SMI/2016/WindowsSettings">PerMonitorV2</dpiAwareness>
    </windowsSettings>
  </application>
</assembly>
```

An interesting bit of fun can be had here by adding Windows support for UTF-8 as the default character set for the application by adding the following:

`<activeCodePage xmlns="http://schemas.microsoft.com/SMI/2019/WindowsSettings">UTF-8</activeCodePage>`

Unfortunately, WinRT still works in 16-bit Unicode (std::wstring) so it doesn't really help us with our cpp/winrt apps. Might be fun if you're still working in an old win32 app though as in theory at least you could use all the non-wide string functions with standard *char and get free unicode support!

### App.xaml

Next we see the `App.xaml` file and a nested collection of matched `.cpp` / `.h` files. 

These are the main application definition files. I suppose you could say they replace the old `winMain()` function found in win32 apps. 

`App.xaml` contains some of the actual UI definition in the form of XML based XAML. [Microsoft Documentation here](https://learn.microsoft.com/en-us/windows/apps/develop/platform/xaml/xaml-overview). Our main GUI elements will be in `MainWindow.xaml` but here I guess we can store some custom ResourceDictionary elements. We'll probably just leave it alone and focus more on `MainWindow.xaml`.

**`App.xaml`**
```xaml
<?xml version="1.0" encoding="utf-8"?>
<Application
    x:Class="WinUIApp.App"
    xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
    xmlns:local="using:WinUIApp">
    <Application.Resources>
        <ResourceDictionary>
            <ResourceDictionary.MergedDictionaries>
                <XamlControlsResources xmlns="using:Microsoft.UI.Xaml.Controls" />
                <!-- Other merged dictionaries here -->
            </ResourceDictionary.MergedDictionaries>
            <!-- Other app resources here -->
        </ResourceDictionary>
    </Application.Resources>
</Application>
```

### App.xaml.h ###

Next up is the actual C++ code for our app. Huzzah! 

First thing you might notice is we're using Pre-Compiled Headers (`#include "pch.h"`) in this project. cpp/winrt has a LOT of includes. Every single WinRT library has been projected into C++ as a separate header file. Placing these into `pch.h` helps reduce compile times, although we'll soon see that compile times will still be an ever-present problem win cpp/winrt. Important to note because any new `.cpp` file you add to the project will need to include the `pch.h` header or have Pre-Compiled Headers disabled for that compilation unit or you'll get an error that it's missing PCH.

Next, looking at the header file, we see a reference to some weird `#include "App.xaml.g.h"` line. Anything with a ".g" means it's part of the auto-generated support structure for cpp/winrt. The ".g" stands for "generated". You can take a peek at that generated header file (you may have to build the project at least once before it will actually exist). These support structures are automatically laid out when you select Add, New Item... Blank Page (C++/WinRT) in Visual Studio.

You'll notice that the App class inherits from AppT and is using CRTP to do static polymorphism. AppT comes from the auto-generated .g files but inherits `Microsoft::UI::Xaml::ApplicationT<>`. 

Like many modern apps, there are functions that get called at various events in application lifetime. These functions can be overwritten with custom code. I think they only give us `OnLaunched()` by default.

You notice also an `implementation` namespace - we'll go over that a little later, but essentially there's an internal namespace (used via the `implementation` namespace to give C++  direct access to the C++ object when needed) and an external namespace (which only has access to the externally defined object properties found in the IDL, which are retrieved via COM). So some care must be used when and when not to use the `implementation` namespace in our code. [Some documentation can be found here](https://learn.microsoft.com/en-us/windows/apps/develop/cpp-winrt/author-apis)

**`App.xaml.h`**
```c++
#pragma once

#include "App.xaml.g.h"

namespace winrt::WinUIApp::implementation
{
    struct App : AppT<App>
    {
        App();

        void OnLaunched(Microsoft::UI::Xaml::LaunchActivatedEventArgs const&);

    private:
        winrt::Microsoft::UI::Xaml::Window window{ nullptr };
    };
}
```

### App.xaml.cpp ###

Next we have our actual `.cpp` file. Being responsible for instantiating the main App object, all it really does is execute the Constructor and override the OnLaunched() function to make a main window based off the `MainWindow` class and `Activate()` it. There's some sample debug exception handling code in the Constructor that comes with the template, probably intended to help catch unhandled exceptions.

**`App.xaml.cpp`**
```c++
#include "pch.h"
#include "App.xaml.h"
#include "MainWindow.xaml.h"

using namespace winrt;
using namespace Microsoft::UI::Xaml;

// To learn more about WinUI, the WinUI project structure,
// and more about our project templates, see: http://aka.ms/winui-project-info.

namespace winrt::WinRT_with_Claude::implementation
{
#include "pch.h"
#include "App.xaml.h"
#include "MainWindow.xaml.h"

using namespace winrt;
using namespace Microsoft::UI::Xaml;

// To learn more about WinUI, the WinUI project structure,
// and more about our project templates, see: http://aka.ms/winui-project-info.

namespace winrt::WinUIApp::implementation
{
    /// <summary>
    /// Initializes the singleton application object.  This is the first line of authored code
    /// executed, and as such is the logical equivalent of main() or WinMain().
    /// </summary>
    App::App()
    {
        // Xaml objects should not call InitializeComponent during construction.
        // See https://github.com/microsoft/cppwinrt/tree/master/nuget#initializecomponent

#if defined _DEBUG && !defined DISABLE_XAML_GENERATED_BREAK_ON_UNHANDLED_EXCEPTION
        UnhandledException([](IInspectable const&, UnhandledExceptionEventArgs const& e)
        {
            if (IsDebuggerPresent())
            {
                auto errorMessage = e.Message();
                __debugbreak();
            }
        });
#endif
    }

    /// <summary>
    /// Invoked when the application is launched.
    /// </summary>
    /// <param name="e">Details about the launch request and process.</param>
    void App::OnLaunched([[maybe_unused]] LaunchActivatedEventArgs const& e)
    {
        window = make<MainWindow>();
        window.Activate();
    }
}

```

### MainWindow.xaml ###

As we begin to build our our application GUI, we'll be adding XAML elements by hand to this file. Unfortunately, in the cpp/winrt workflow, the visual XAML designer that's part of other frameworks just isn't available to us. The best we can do is edit this by hand, probably with sample XML from the [WinUI Gallery](https://github.com/microsoft/WinUI-Gallery). Things like a menu bar, menu items, keyboard shortcuts, etc will go here. The template begins with an empty `<Grid>` element.

**`MainWindow.xaml`**
```xaml
<?xml version="1.0" encoding="utf-8"?>
<Window
    x:Class="WinUIApp.MainWindow"
    xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
    xmlns:local="using:WinUIApp"
    xmlns:d="http://schemas.microsoft.com/expression/blend/2008"
    xmlns:mc="http://schemas.openxmlformats.org/markup-compatibility/2006"
    mc:Ignorable="d"
    Title="WinUIApp">

    <Grid>

    </Grid>
</Window>
```

We will need a way to display content in the UI that is bound to our C++ code. The XAML definition will use the `bind` keyword to bind UI elements to our variables in C++. Because XAML and cpp/winrt live in two different worlds, we must pre-define any data that must pass between the two using a special language called "Interface Definition Language" - a C like language where we will define structs, constructors, etc for this data and follow it up with matching C++ code. We'll get to all that shortly, but conceptually XAML and C++ live in two different worlds and any data that will be accessible to both needs to be defined in IDL so each knows how to read and write to it. We'll also have to figure out how to define these objects in C++ so they can both send and receive updates when their values change in either the XAML GUI or in C++.

Below is the sample `.idl` file included with the template and used by MainWindow. It defines MainWindow as inheriting from `Microsoft.UI.Xaml.Window` (notice the single `:` instead of the double `::` used in C++). I suppose that's what glues MainWindow to both XAML and C++. 

Additionally, there's an `Int32 MyProperty` definition, meaning this data object contains both the Window and an integer object that can be accessed both in the GUI XAML and C++.

**`MainWindow.idl`**
```
namespace WinUIApp
{
    [default_interface]
    runtimeclass MainWindow : Microsoft.UI.Xaml.Window
    {
        MainWindow();
        Int32 MyProperty;
    }
}
```

Next is the `.h` file for MainWindow. Note how it includes the `.g` auto-generated cpp/winrt support file and we're using the `implementation` namespace (because we're defining the C++ actual implementation). We have a declared and defined Constructor and we have **getter/setter** entries for the `MyProperty` value. C++ has no real getter/setter paradigm, but the style shown is how XAML expects getter/setter entries to exist for any data defined in IDL. 

I'm not sure what the `factory_implementation` namespace does. I assume it has something to do with how the MainWindow class is instantiated by COM, allowing us to define what happens when a new object is requested by COM (although I'm not sure why we wouldn't just use the Constructor to set this behavior). If you take a look at the `MainWindowT<>` class, it comes from the `.g` file and inherits `IActivationFactory`. `MainWindowT<>` defines `GetRuntimeClassName()` and `ActivateInstance()` functions.

**`MainWindow.xaml.h`**
```c++
#pragma once

#include "MainWindow.g.h"

namespace winrt::WinUIApp::implementation
{
    struct MainWindow : MainWindowT<MainWindow>
    {
        MainWindow()
        {
            // Xaml objects should not call InitializeComponent during construction.
            // See https://github.com/microsoft/cppwinrt/tree/master/nuget#initializecomponent
        }

        int32_t MyProperty();
        void MyProperty(int32_t value);
    };
}

namespace winrt::WinUIApp::factory_implementation
{
    struct MainWindow : MainWindowT<MainWindow, implementation::MainWindow>
    {
    };
}
```

Finally we have the `.cpp` file for MainWindow. It does a "does this header exist, if so include it" for the auto-generated files. This allows successful one-click builds (older versions of cpp/winrt required building *twice* - once to create the auto-generated files and then again for the whole project). We have the `implementation` namespace indicating we're defining the internal C++ "implementation" code. The sample code just throws an exception if it's called, since it's not finished yet.

**`MainWindow.cpp`**
```c++
#include "pch.h"
#include "MainWindow.xaml.h"
#if __has_include("MainWindow.g.cpp")
#include "MainWindow.g.cpp"
#endif

using namespace winrt;
using namespace Microsoft::UI::Xaml;

// To learn more about WinUI, the WinUI project structure,
// and more about our project templates, see: http://aka.ms/winui-project-info.

namespace winrt::WinUIApp::implementation
{
    int32_t MainWindow::MyProperty()
    {
        throw hresult_not_implemented();
    }

    void MainWindow::MyProperty(int32_t /* value */)
    {
        throw hresult_not_implemented();
    }
}
```

### Other Stuff ###

### WIL ###

The Windows Implementation Library is a collection of helper functions and optimized data structures. I don't think it's required to do cpp/winrt or WinUI3. I actually removed it as I don't really *intend* to use it (but might, if it's mentioned somewhere in the docs as recommended). For now, I don't see the need, so I took it out of my nuget packages and removed the wil.* files.

### Here's what *Claude* says about the `wil` files above: ###

Both are Visual Studio debugger customization files, part of the WIL (Windows Implementation Library) package we saw referenced in pch.h earlier — not something you need to edit, but worth knowing what they do.

.natvis (Native Visualizer) — an XML file telling the Visual Studio debugger how to display specific C++ types in a readable way when you hover over a variable or view it in the Watch/Locals window. Without one, complex template types (like WIL's or WinRT's internal smart-pointer/wrapper types) often show up as a confusing wall of raw internal member data. wil.natvis specifically teaches the debugger to show WIL's types (like the property helpers we discussed) in a clean, human-readable format instead.

.natstepfilter (Native Step Filter) — tells the debugger which functions to skip over automatically when you use Step Into (F11). Without this, stepping into what looks like "your own code" might accidentally dive deep into WIL's internal plumbing/helper functions — tedious, unhelpful noise during debugging. This file tells the debugger "don't step into these specific internal WIL functions, just run them and continue," keeping your debugging experience focused on your actual application logic.

Practical takeaway: both are automatically brought in by the WIL NuGet package (recall Microsoft.Windows.ImplementationLibrary, visible in your .vcxproj's package list) — they're debugging quality-of-life tools, not something you write, edit, or need to understand deeply. Safe to ignore entirely; they're doing their job silently in the background whenever you debug.
