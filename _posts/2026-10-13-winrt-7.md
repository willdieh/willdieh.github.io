## Multi-Threading ##

[Last time]({% post_url 2026-10-03-winrt-6 %}) we touched briefly on threading models in cpp/winrt. I don't claim to be any kind of expert on this topic but I'd like to work through an example that shows how things must generally be done on the main UI thread when it comes to updating UI elements to keep bad things from happening.

### Background ###

Because winrt runs through COM, behind the scenes it follows the COM workflow. Typically, when starting up COM in an old Win32 Windows application, you would initialize COM by first asking for a specific type of *apartment*. That apartment, in which all the COM activity happens, can be either single-threaded (default) or multi-threaded. You can work with multiple single-threaded apartments but can only ever have at most *one* multi-threaded apartment.

When working with objects *within* an apartment, objects are modified *directly* by the apartment's thread(s). 

When attempting to work with an object in *another* apartment, the object must be *marshalled* between the two apartments. This is done by calling special COM functions to create a proxied reference to the object and passing the reference to the external apartment.

External access to COM objects inside a single-threaded apartment is provided via the Windows message queue. By forcing all access through a single queue, data contention issues are avoided within that single-threaded apartment. 

External access to COM objects inside a multi-threaded apartment is *not* synchronized using the Windows message queue - it's not synchronized at all! Multiple external requests can be processed simultaneously by a multi-threaded apartment, each on a different apartment thread, so it is necessary to protect objects with proper synchronization primitives like mutexes. 

### WinUI and C++/Winrt ###

WinUI applications are built with XAML and default to a single-threaded apartment. If you look in the `Generated Files` folder of your project (after hitting Build Solution at least once to fire off the XAML compiler), you'll see an auto-generated `App.xaml.g.hpp` file that contains the default `wWinMain` function. In there you'll notice a call to `winrt::init_apartment(winrt::apartment_type::single_threaded);` whereby our single-threaded COM apartment is created. All XAML UI operations must happen on this single thread. XAML objects check the thread requesting access and throw `RPC_E_WRONG_THREAD` if it's not the main UI thread. 

Custom runtime classes, like our `Person` class, are by default a special kind of COM object known as an [*agile* object](https://learn.microsoft.com/en-us/windows/apps/develop/cpp-winrt/agile-objects). Agile objects implement the `IAgileObject` COM interface. These agile objects are declaring that they do not participate in the standard marshalling process. Instead, they are stating that they can be accessed by any apartment directly by pointer, without marshalling. Agile objects run on whatever thread attempts to access them. If multiple threads access an agile object, it must be properly thread synchronized in code.

It's possible to opt out of the default agile implementation by adding `winrt::non_agile` to the inherited types of a C++ runtime class implementation like `WinUIApp::implementation::Person : PersonT<Person, winrt::non_agile, ...>`. This would allow the object to provide the marshalling interfaces and be marshalled by reference using the standard COM functions as described above instead of as raw pointers.

If your agile runtime class needs to access and update a COM object that isn't agile (most *are* agile), you can wrap that non-agile object in an agile reference like `winrt::agile_ref<[non_agile_typename]> agileThing {nonAgileThing};` or `auto agileThing = winrt::make_agile(nonAgileThing);`. This would allow you to access that non-agile object from whatever thread your agile object is in using `agileThing.get()`, automagically performing marshalling into that non-agile object's apartment. The only catch is you have to create the reference on the same thread as the non-agile object (or properly marshall it onto your current thread). Sigh. Hope we don't need to do this.

I expect we will just be running on the main UI thread. For those situations where we need to do work on a background thread, it's probably easiest to just stay in the agile world where threads don't matter but always switch back to our main UI thread before updating the UI with our results. We can do this by capturing the main UI thread before switching to a background thread then switching back to the UI thread when we're done.

## Open File ##

Let's put all this into practice by working with the `FilePicker` to open a CSV file, process it on a background thread to create `Person` objects, then update our UI.

Our first run-through will be blissfully ignorant of threads and all that nonsense! Let's find out what happens!

### CSV Format ###

Create a new file in the project folder called `people.csv` and add a couple people, one line at a time like this:

**`people.csv`**
```txt
Frank,Delgado,1983-03-11,555-0106,frank@example.com
Grace,Thompson,1998-07-22,555-0107,grace@example.com
Henry,Abernathy,1969-11-08,555-0108,henry@example.com
Iris,Chen,2001-01-17,555-0109,iris@example.com
```

### `FilePicker` ###

Update your `OnOpenClick` function in `MainWindow.xaml.cpp` to add a `*.csv` filter and a call to a new function we'll write that parses and loads a CSV file

```c++

#include <fstream>  // for std::wifstream
#include <chrono>   // for DateTime parsing
#include <charconv> // for std::from_chars
...
winrt::fire_and_forget MainWindow::OnOpenClick(IInspectable const& sender, RoutedEventArgs const& e)
{
    // Return the handle id for this window (necessary for non-packaged apps)
    FileOpenPicker openPicker(this->AppWindow().Id());

    // Set a filter to *.csv
    openPicker.FileTypeFilter().Append(L".csv");
    
    // co_await suspends this function and returns to the caller until 
    // the FilePicker returns an object at which point it resumes.
    // The suspended work done by FilePicker may or may not be done on
    // the same thread as this function.
    // In c++/winrt, co_await resumes on the calling thread by default 
    // which should be the main UI thread that MainWindow is running on.        
    auto file = co_await openPicker.PickSingleFileAsync();

    if (file)
    {
        std::vector<WinUIApp::Person> newPeople = LoadCSV(file.Path());
        
        m_people.ReplaceAll(newPeople);            
    }
}
...
std::vector<WinUIApp::Person> MainWindow::LoadCSV(hstring const& path)
{
    std::vector<WinUIApp::Person> newPeople{};

    // Open our file at the end (so we can get size)
    std::ifstream file{ path.c_str(), std::ios::binary | std::ios::ate };
    if (file)
    {
        // Create a string to act as a file buffer
        std::string fileBuffer(file.tellg(), '\0');

        // Rewind file
        file.seekg(0);            

        // Fill file buffer
        if (file.read(fileBuffer.data(), fileBuffer.size()))
        {
            // No need to keep the file open after reading it
            file.close();

            // We'll use std::string_view objects to point to various parts of the file buffer
            
            // Set "remaining" string_view to the beginning of the file buffer
            std::string_view remaining{ fileBuffer };

            while (!remaining.empty())
            {
                // Split off the next line
                size_t lineEnd = remaining.find('\n');

                // Another string_view from beginning to '\n'
                std::string_view line = remaining.substr(0, lineEnd);

                // Set "remaining" string_view to begin just after the '\n' or empty if nothing left.
                remaining = (lineEnd == std::string_view::npos) ? std::string_view{} : remaining.substr(lineEnd + 1);

                // Strip and \r from end of line (for Windows \r\n line endings)
                if (!line.empty() && line.back() == '\r') line.remove_suffix(1);
                
                // Setup an array to hold string_view objects to each field value
                constexpr size_t MAXFIELDS = 5;
                std::string_view fields[MAXFIELDS];
                size_t count = 0;

                // Split the line into fields
                while (count < MAXFIELDS)
                {
                    // find the next comma
                    size_t comma = line.find(',');

                    // set a field string_view from beginning to first comma
                    fields[count++] = line.substr(0, comma);

                    // if nothing after the comma, break 
                    if (comma == std::string_view::npos) break;

                    // remove everything up after to the comma from the front of the line
                    line.remove_prefix(comma + 1);
                }

                // Skip blank or short lines
                if (count != MAXFIELDS) continue;

                // Parse date
                std::string_view dob = fields[2];

                // if DOB is not 'YYYY-MM-DD' skip this entire line
                if (dob.size() != 10) continue;

                // Weird that the year is int but month/day is unsigned int
                int y{};
                unsigned int m{}, d{};

                // Parse using c++20 std::from_chars
                std::from_chars(dob.data(), dob.data() + 4, y);
                std::from_chars(dob.data() + 5, dob.data() + 7, m);
                std::from_chars(dob.data() + 8, dob.data() + 10, d);

                // Create a year_month_date object from values
                std::chrono::year_month_day date{
                    std::chrono::year{y},
                    std::chrono::month{m},
                    std::chrono::day{d}
                };

                // Skip entire line if date is invalid
                if (!date.ok()) continue;
                
                // Create our Person object using the fields
                // Remember that WinUIApp::Person is a runtime class (COM object) so it's
                // just a heap allocated reference counted pointer.
                // Each winrt::hstring is the same, new heap allocated HSTRING objects
                // created from the string_view objects.
                newPeople.push_back(
                    WinUIApp::Person{
                        winrt::to_hstring(fields[0]),
                        winrt::to_hstring(fields[1]),
                        winrt::clock::from_sys(std::chrono::sys_days{date}),
                        winrt::to_hstring(fields[3]),
                        winrt::to_hstring(fields[4])
                    }
                );
            }
        }
    }
    
    // newPeople is basically a vector of pointers to reference counted, heap allocated COM objects
    return newPeople;
}
```

The `LoadCSV` function will read the path returned by the `FilePicker` and parse the CSV into new `WinUIApp::Person` objects. Remember, these objects are created on the heap and return only a reference counted pointer. When we add them to the temporary `newPeople` vector, we are just storing pointers. 

Finally, we replace the guts of our `IObservableVector m_people` with the temporary vector. It's pretty cool how this works.

- `ReplaceAll` doesn't actually take a `std::vector`, it takes a `winrt::array_view<T const>`
- `winrt::array_view` is a lightweight, non-owning view, similar to `std::span`
- The `IObservableVector` uses the view to copy the elements into its own internal storage 
- Since each `Person` is a reference-counted pointer, this just increments the reference counts; no `Person` objects are duplicated!
- A `VectorChanged` event with `CollectionChange::Reset` is fired, telling the `ListView` to rebuild its whole list rather than processing one change per item
- When `newPeople` goes out of scope, its references are released and the `Person` objects stay alive because `m_people` now holds them.

If you compile and run this code, it will (hopefully) work great because, even with a co_await, the `OnOpenClick` function does all its work on the main UI thread. 

## Background Thread ##

Let's update our code to load and parse the CSV on a background thread and see what happens

**`MainWindow.xaml.cpp`**
```c++
...
winrt::fire_and_forget MainWindow::OnOpenClick(IInspectable const& sender, RoutedEventArgs const& e)
{
    // Keep a reference to MainWindow alive so that, even if MainWindow somehow
    // closes during our coroutine suspend and background work, it will stay open
    // because we hold a reference to it. DO THIS BEFORE SUSPENSION!
    auto strong_reference = this->get_strong();

    // Return the handle id for this window (necessary for non-packaged apps)
    FileOpenPicker openPicker(this->AppWindow().Id());

    // Set a filter to *.csv
    openPicker.FileTypeFilter().Append(L".csv");
    
    // co_await suspends this function and returns to the caller until 
    // the FilePicker returns an object at which point it resumes.
    // The suspended work done by FilePicker may or may not be done on
    // the same thread as this function.
    // In c++/winrt, co_await resumes on the calling thread by default 
    // which should be the main UI thread that MainWindow is running on.        
    auto file = co_await openPicker.PickSingleFileAsync();

    if (file)
    {
        // Copy the path before suspending (may not exist after)
        hstring path = file.Path();

        // suspend function, returning immediately
        // remaining work will be done on a background thread
        co_await winrt::resume_background();

        std::vector<WinUIApp::Person> newPeople = LoadCSV(path);
        
        // FAIL? still on background thread. 
        // XAML will complain about invalid thread access when
        // event is fired to update UI object
        m_people.ReplaceAll(newPeople);            
    }
}
...
```
