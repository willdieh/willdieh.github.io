## Threading Gotchas #1 ##

### Strong References ###

You may have noticed that `OnOpenClick()` is actually a C++ coroutine. When we hit that `co_await` keyword, the function is suspended until something wakes it back up. Because of this, it's possible that any state that existed before the suspend point is actually GONE when the function is finally resumed. For example, the application may have been closed before the FileOpenPicker ever completed its result, meaning the parent window and xaml and everything else is now gone - poof!

While having the main window close right out from under us sounds bad, in reality I doubt we'd actually care at that point whether `FileOpenPicker` existed or not as the program would be closed. Regardless, this points out a very important concept when working with coroutines: It's very important to generate something called a "Strong Reference" to an underlying COM object (in this case, our `MainWindow`) any time a coroutine might be suspended to tell the COM system to increment that reference counting pointer one more time so it doesn't think nobody is using this object until we're finished with our coroutine. [Documentation Here](https://learn.microsoft.com/en-us/windows/apps/develop/cpp-winrt/weak-references).

Consequently, we should always create a strong reference before any suspension point like so:

**`MainWindowXaml.cpp`**
```c++
    ...
    winrt::fire_and_forget MainWindow::OnOpenClick([[maybe_unused]] IInspectable const& sender, [[maybe_unused]] RoutedEventArgs const& e)
    {
        // Keep a reference to MainWindow alive so that, even if MainWindow somehow
        // closes during our coroutine suspend and background work, it will stay open
        // because we hold a reference to it. DO THIS BEFORE SUSPENSION!
        auto strong_reference = this->get_strong();
    ...
```

## Threading Gotchas #2 ##

### Non-Agile objects ###

The `file` we get back from `PickSingleFileAsync()` may or may not be an agile object (it *is*, as are most winrt objects, but let's just pretend we don't know). Because we're about to `co_await` again in order to switch back to the main UI thread, we might have to deal with marshalling `file` onto the other thread. 

It is possible to use `winrt::agile_ref` to create a agile reference to a non-agile type. [Documentation here](https://learn.microsoft.com/en-us/windows/apps/develop/cpp-winrt/agile-objects#agile-references-winrtagile_ref). An easier solution is to just copy only the data we need from `file` into an agile safe object so it's safe to pass around to different threads. 

In our case, we only need `file.Path()` which is just an `hstring` and is agile. The easiest thing to do then is just copy the path into an `hstring` and use the `hstring` after the switch to the main UI thread like this:

**`MainWindowXaml.cpp`**
```c++
    winrt::fire_and_forget MainWindow::OnOpenClick([[maybe_unused]] IInspectable const& sender, [[maybe_unused]] RoutedEventArgs const& e)
    {
    ...
    auto file = co_await openPicker.PickSingleFileAsync();
    
    if (file)
    {
        // FilePicker may or may not be an agile object. Just copy
        // the path into a plain old hstring so we know we can safely
        // access it on another thread.
        hstring path = file.Path();
    
        // suspend function, returning immediately
        // remaining work will be done on a background thread
        co_await winrt::resume_background();
    
        std::vector<WinUIApp::Person> newPeople = LoadCSV(path);
    ...
```

## Threading Gotchas #3 ##

### DispatcherQueue ###

[Last Time]({{% post_url 2025-10-13-winrt7 %}}) we successfully spun off some work on a background thread and then displayed the output on the UI. To do this, we had to capture the main UI thread in a `winrt::apartment_context` object before suspending our coroutine to a background thread and performing the work. Once the work was done, we suspended back onto the main UI thread using the same `winrt::apartment_context` object before updating the UI. 

The above method of capturing the apartment context so we can return to the main UI thread only works if you know the apartment is actually *on* the main UI thread. Since `MainWindow` certainly is, we don't need to worry. If however, we wanted to make a more generalized function, that could be called from any thread and still update an object on the main UI thread, we need a slightly different approach.

Per the [Microsoft Documentation](https://learn.microsoft.com/en-us/windows/apps/develop/cpp-winrt/concurrency-2#programming-with-thread-affinity-in-mind), there's a more generalized approach. When we don't know what thread we're on but need to identify the main UI thread so we can switch to it before a UI update, we must identify something called a `DispatcherQueue` associated with the XAML UI element we want to update. If we can grab this magical `DispatcherQueue`, we can use it to get the main UI thread. 

Once we have a `DispatcherQueue`, we can pass it to a special `winrt::resume_foreground` function with a `co_await` to switch to the UI thread and then perform our update. XAML elements have these mystical beasts so we need a way to expose the XAML element to C++. 

To expose a XAML element to C++, all we have to do is give it a `x:Name` attribute in the `.xaml` file. This will cause the xaml compiler to create a getter function in the auto generated code supporting the class implementing the XAML object (in this case, `MainWindow`). You can see the auto generated code in the `MainWindowT` class found in `MainWindow.xaml.g.h` in the `Generated Files` folder of the project.

On the `MainWindow` XAML object our `Person` objects are displayed in a `ListView`. Let's give that `ListView` a `x:Name` attribute so we can access it in C++. Remember, in the `MainWindow.xaml` file, attributes that begin with `x:` are defined as coming from the URI `http://schemas.microsoft.com/winfx/2006/xaml` which means they're part of the Microsoft XAML spec.

**`MainWindow.xaml`**
```xaml
...
<ListView Grid.Row="1" ItemsSource="{x:Bind People}" x:Name="PeopleListView">
...
```

Now we can access it in our C++ code!

**`MainWindow.xaml.cpp`**
```c++
...
#include <winrt/Microsoft.UI.Dispatching.h> // For winrt::resume_foreground (missing!) and DispatcherQueue 
...
winrt::fire_and_forget MainWindow::OnOpenClick([[maybe_unused]] IInspectable const& sender, [[maybe_unused]] RoutedEventArgs const& e)
{
    // Return the handle id for this window (necessary for non-packaged apps)
    FileOpenPicker openPicker(this->AppWindow().Id());

    // Set a filter to *.csv
    openPicker.FileTypeFilter().Append(L".csv");
    
    // co_await suspends this function and returns to the caller until 
    // the FilePicker returns an object at which point it resumes.
    // The suspended work done by FilePicker may or may not be done on
    // the same thread as this function.
    // In c++/winrt, co_await resumes on the calling thread by default 
    // which should be the main UI thread that MainWindow is running on.        
    auto file = co_await openPicker.PickSingleFileAsync();

    if (file)
    {
        // suspend function, returning immediately
        // remaining work will be done on a background thread
        co_await winrt::resume_background();

        std::vector<WinUIApp::Person> newPeople = LoadCSV(file.Path());
        
        // switch back to the main UI thread
        co_await winrt::resume_foreground(PeopleListView().DispatcherQueue());

        // XAML will complain about invalid thread access when
        // event is fired to update UI object if not on main UI thread!
        m_people.ReplaceAll(newPeople);            
    }
}
...
```

### Broken Much?! ###

So, yeah, you may notice the above doesn't compile. Even though it's documented as supposed to work, turns out there was a namespace split when WinUI3 was released. What used to be in the `winrt::Windows` namespace moved to the `winrt::Microsoft` namespace. This affects our `DispatcherQueue` and the `winrt::resume_foreground` function. 

There is a `winrt::resume_foreground` function in `<winrt/Windows.System.h>` header, and it takes a `DispatcherQueue`, but it only works with the old `winrt::Windows::System` namespace. Even the [documentation](https://learn.microsoft.com/en-us/uwp/cpp-ref-for-winrt/resume-foreground) for the `winrt::resume_foreground` function still references the old namespace header files. 

The fact is that the WinUI3 project didn't add the necessary `winrt::resume_foreground` function in the updated `<winrt/Microsoft.UI.Dispatching.h>` header. There's a whole thing on it in [StackOverflow](https://stackoverflow.com/questions/68338871/winui3-desktop-c-cant-compile-winrtresume-foregroundmicrosoftsystemdi), a related post by [Raymond Chen](https://devblogs.microsoft.com/oldnewthing/20221116-00/?p=107416/), and a [pull request](https://github.com/microsoft/cppwinrt/pull/1574) that looks ready to go but hasn't been approved yet (I put in a comment hoping for progress). 

The [official answer](https://learn.microsoft.com/en-us/windows/apps/windows-app-sdk/migrate-to-windows-app-sdk/guides/threading#migrate-winrtresume_foreground-cwinrt) is to use the WIL (Windows Implementation Library - you know, that thing we removed from the project waaaay back in the first post?). 

Hopefully someday we'll get some love here, but at least we got to take a look at it. 

### Coroutine Temp Fix ###

For fun, let's say we wanted to fix this by hand. We need have to write our own C++ awaitable coroutine object that accepts the newer WinUI3 `Microsoft::UI::Dispatching::DispatcherQueue` type. Yikes.

Someday I'd love to write a blog entry just on coroutines. They're super interesting. Instead, we'll just take a look at the code in the [Microsoft WIL repository](https://github.com/microsoft/wil/blob/master/include/wil/cppwinrt_helpers.h) that creates the corrected `resume_foreground` coroutine.

Here's a modified version that should be suitable to use as `util::resume_foreground` instead of `winrt::resume_foreground`:

**`util.h`**
```c++
#pragma once

#include <coroutine>
#include <winrt/base.h>
#include <winrt/Microsoft.UI.Dispatching.h>

// Adapted from wil/cppwinrt_helpers.h (Windows Implementation Library)
// Copyright (c) Microsoft. Licensed under the MIT License.
// https://github.com/microsoft/wil

namespace util::details
{
    struct dispatched_handler_state
    {
        std::coroutine_handle<> handle{};
        bool orphaned = false;
    };

    struct dispatcher_handler
    {
        explicit dispatcher_handler(dispatched_handler_state* state) noexcept
            : m_state(state) {};
        dispatcher_handler(dispatcher_handler&& other) noexcept
            : m_state(std::exchange(other.m_state, nullptr)) {};
        ~dispatcher_handler()
        {
            if (m_state && m_state->handle)
            {
                m_state->orphaned = true;
                Complete();
            }
        }

        void operator()() {Complete();};
        void Complete()
        {
            auto state = std::exchange(m_state, nullptr);
            std::exchange(state->handle, {}).resume();
        };

        dispatched_handler_state* m_state;
    };
}

namespace util
{
    using winrt::Microsoft::UI::Dispatching::DispatcherQueue;
    using winrt::Microsoft::UI::Dispatching::DispatcherQueuePriority;
    using winrt::Microsoft::UI::Dispatching::DispatcherQueueHandler;

    // Resumes the coroutine on the dispatcher queue's thread, or throws
    // hresult_error(ERROR_NO_TASK_QUEUE) if the queue could not run the work item.
    [[nodiscard]] inline auto resume_foreground(
        DispatcherQueue const& dispatcher,
        DispatcherQueuePriority priority = DispatcherQueuePriority::Normal)
    {
        struct awaitable
        {
            awaitable(DispatcherQueue const& dispatcher, DispatcherQueuePriority priority) noexcept
                : m_dispatcher(dispatcher), m_priority(priority) {
            }

            bool await_ready() const noexcept
            {
                return false; // always queue, even if already on the target thread
            }

            void await_suspend(std::coroutine_handle<> handle)
            {
                m_state.handle = handle;
                DispatcherQueueHandler handler{ details::dispatcher_handler(&m_state) };
                try
                {
                    // TryEnqueue's return value isn't relied on; the handler's destructor
                    // detects a work item that never ran.
                    m_dispatcher.TryEnqueue(m_priority, handler);
                }
                catch (...)
                {
                    m_state.handle = nullptr; // the exception resumes the coroutine instead
                    throw;
                }
            }

            void await_resume() const
            {
                if (m_state.orphaned)
                {
                    throw winrt::hresult_error(static_cast<winrt::hresult>(0x800701ab)); // ERROR_NO_TASK_QUEUE
                }
            }

        private:
            DispatcherQueue const& m_dispatcher;
            DispatcherQueuePriority const m_priority;
            details::dispatched_handler_state m_state;
        };

        return awaitable{ dispatcher, priority };
    }
}
```
