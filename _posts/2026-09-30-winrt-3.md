## MainWindow.xaml

Thus far in the tutorial, we've only added the default WinUI3 application from the Visual Studio template. 

Looking at the initial `MainWindow.xaml` file, we see there's nothing in the main window except an empty `<Grid>` element. 

We need at least one parent element into which we can place our `<MenuBar>`. The `<Window>` element would work but can only hold a single "content" object. This means if we add our `<MenuBar>` directly to `<Window>` we wouldn't be able to add anything else like a `<Grid>` or a `<Canvas>`. You'll get an error that `The Property 'Content' is set more than once` if you try to add more than one object to the `<Window>` element. So we'll just stick our `<MenuBar>` under the existing `<Grid>` element.

**`MainWindow.xaml`**
```xaml
<?xml version="1.0" encoding="utf-8"?>
<Window
    x:Class="WinUIApp.MainWindow"
    xmlns="http://schemas.microsoft.com/winfx/2006/xaml/presentation"
    xmlns:x="http://schemas.microsoft.com/winfx/2006/xaml"
    xmlns:local="using:WinUIApp"
    xmlns:d="http://schemas.microsoft.com/expression/blend/2008"
    xmlns:mc="http://schemas.openxmlformats.org/markup-compatibility/2006"
    mc:Ignorable="d"
    Title="WinUIApp">
    <Grid>
        <Grid.RowDefinitions>
            <RowDefinition Height="Auto"/>
            <RowDefinition Height="*"/>
        </Grid.RowDefinitions>
        <MenuBar Grid.Row="0">
            <MenuBarItem Title="File" AccessKey="F" >
                <MenuFlyoutItem Text="Open..." Click="OnOpenClick" AccessKey="O">
                    <MenuFlyoutItem.KeyboardAccelerators>
                        <KeyboardAccelerator Modifiers="Control" Key="O"/>
                    </MenuFlyoutItem.KeyboardAccelerators>
                </MenuFlyoutItem>
                <MenuFlyoutItem Text="Exit" Click="OnExitClick" AccessKey="X"/>
            </MenuBarItem>
            <MenuBarItem Title="View" AccessKey="V">
                <RadioMenuFlyoutItem Text="Landscape" AccessKey="L" GroupName="OrientationGroup" Click="OnOrientationClick"/>
                <RadioMenuFlyoutItem Text="Portrait" AccessKey="P" GroupName="OrientationGroup" IsChecked="True" Click="OnOrientationClick"/>
                <MenuFlyoutSeparator/>
                <RadioMenuFlyoutItem Text="Small icons" AccessKey="S" GroupName="SizeGroup" Click="OnSizeClick"/>
                <RadioMenuFlyoutItem Text="Medium icons" AccessKey="M" IsChecked="True" GroupName="SizeGroup" Click="OnSizeClick"/>
                <RadioMenuFlyoutItem Text="Large icons" AccessKey="G" GroupName="SizeGroup" Click="OnSizeClick"/>
            </MenuBarItem>
        </MenuBar>
    </Grid>
</Window>
```
### RowDefinitions

Grids are pretty rigid buggers. We have to define how many rows we have and the properties of each row. We'll just add two rows for now, the first one set to `Auto` height and the second using the rest of the screen.

### MenuBar

Main menubar tag

- `Grid.Row="0"` Unfortunately, `<Grid>` requires hard-coding locations of all items on the grid. The `<MenuBar>` will be on the top, so set it to row 0

### MenuBarItem

Individual menubar item

- `Title` Sets the menu name
- `AccessKey` Sets the `Alt+<letter>` access key modifier for this menu. To see the access keys, you must first press the `Alt` key

### MenuFlyoutItem

Menubar sub-menu

- `Text` Sets Flyout (sub-menu) name
- `Click` Sets the click handler function name for this menu (to be written in C++)
- `AccessKey` Sets the `Alt+<letter>` access key modifier for this menu. To see the access keys, you must first press the `Alt` key

**KeyboardAccelerators**

Set up global keyboard shortcuts consisting of some modifier key (`Ctrl`, `Alt`, etc) and a regular key (`C`, `X`, etc)

- `Modifiers` Sets the modifier key for the global shortcut
- `Key` Sets the regular key for the global shortcut

### MenuFlyoutSeparator

A cosmetic line for separating menu entries

### RadioMenuFlyoutItem

Adds a Radio Button style menu item

- `Text` Radio button description
- `GroupName` Radio button group (only one active selection per group)
- `IsChecked` whether checked or unchecked

## Click Handlers in C++

If you were to try and compile the project after updating `MainWindow.xaml` as above, you'd get several errors because the click handler functions named in the `Click` attributes haven't been created yet. Let's create them!

There are two click handler styles that I've seen so far. One returns a `winrt::fire_and_forget` and is intended to be **asynchronous** while the other returns `void` and is **synchronous**. 

The parameter types for click handlers are usually an `IInspectable` for the click-sending object and a `RoutedEventArgs` for the specific click arguments unique to that object. Generally, in the click handler function body, you cast the `IInspectable` to the expected type and then call its specific functions to get information. This is the same way the old COM system worked in Win32. You'd get an `IInspectable` from the COM system and then try to cast it to the object you expect it to be in order to access its specific functions. Fun trivia: COM was invented before C++ and virtual functions, so it's serving the same functionality solved by C++'s dynamic polymorphism but requires a manual cast. 

We're not really interested in the menus themselves, so we won't really need to do manual casting yet. But in the future, as we interact with buttons or lists, we may need this information.

**`MainWindow.xaml.h`**
```c++
#pragma once

#include "MainWindow.g.h"

using namespace winrt::Microsoft::UI::Xaml; // For RoutedEventArgs

namespace winrt::WinUIApp::implementation
{
    struct MainWindow : MainWindowT<MainWindow>
    {
        MainWindow()
        {
            // Xaml objects should not call InitializeComponent during construction.
            // See https://github.com/microsoft/cppwinrt/tree/master/nuget#initializecomponent
        }

        // click handlers
        winrt::fire_and_forget OnOpenClick(IInspectable const& sender, RoutedEventArgs const& e);
        void OnExitClick(IInspectable const& sender, RoutedEventArgs const& e);
        void OnOrientationClick(IInspectable const& sender, RoutedEventArgs const& e);
        void OnSizeClick(IInspectable const& sender, RoutedEventArgs const& e);

        int32_t MyProperty();
        void MyProperty(int32_t value);
    };
}

namespace winrt::WinUIApp::factory_implementation
{
    struct MainWindow : MainWindowT<MainWindow, implementation::MainWindow>
    {
    };
}

```

**`MainWindow.xaml.cpp`**
```c++
#include "pch.h"
#include "MainWindow.xaml.h"
#if __has_include("MainWindow.g.cpp")
#include "MainWindow.g.cpp"
#endif


#include <winrt/Microsoft.UI.Windowing.h>   // For AppWindow
#include <winrt/Microsoft.Windows.Storage.Pickers.h>    // For FileOpenPicker

using namespace winrt;
using namespace Microsoft::UI::Xaml;
using namespace winrt::Microsoft::Windows::Storage::Pickers;

// To learn more about WinUI, the WinUI project structure,
// and more about our project templates, see: http://aka.ms/winui-project-info.

namespace winrt::WinUIApp::implementation
{
    winrt::fire_and_forget MainWindow::OnOpenClick(IInspectable const& sender, RoutedEventArgs const& e)
    {
        // Return the handle id for this window (necessary for non-packaged apps)
        FileOpenPicker openPicker(this->AppWindow().Id());

        auto file{ co_await openPicker.PickSingleFileAsync() };
    }

    void MainWindow::OnExitClick(IInspectable const& sender, RoutedEventArgs const& e)
    {
        Application::Current().Exit();
    }

    void MainWindow::OnOrientationClick(IInspectable const& sender, RoutedEventArgs const& e)
    {
    }

    void MainWindow::OnSizeClick(IInspectable const& sender, RoutedEventArgs const& e)
    {
    }

    int32_t MainWindow::MyProperty()
    {
        throw hresult_not_implemented();
    }

    void MainWindow::MyProperty(int32_t /* value */)
    {
        throw hresult_not_implemented();
    }
}

```

We use the `winrt::fire_and_forget` type for menu actions that are expected to wait for user interaction - things like opening a file using a file selector UI element. This return type allows the main UI thread to return while waiting for the user interaction, preventing the application from freezing during that time. The synchronous menu actions should execute immediately.

We're making an **unpackaged** WinUI3 app and this causes some problems with a few WinUI3 components because it creates a window that doesn't have all the fluff generated by a fully packaged application. As a result, for the `FileOpenPicker` object, we have to do some extra work to get the window handle. Thus the extra `this->AppWindow().Id()` call and associated `#include <winrt/Microsoft.UI.Windowing.h>`.

## Fixing C++17 Compiler Errors

If you try to compile now, you'll probably get a few errors like these:

```
#error directive: "C++/WinRT no longer supports pre-standardization coroutines. If you use co_await, switch to /await:strict or upgrade to C++20. If you do not, remove /await from the compiler flags."
namespace "winrt" has no member "fire_and_forget"
```

These are from the `winrt::fire_and_forget` type - this is a wrapper for a coroutines enabled return type. To enable coroutines, you must compile with C++20 (or later). The easiest fix is to set the C++ version to C++20. In the project Properties menu, select Configuration Properties, C/C++, Language, and set C++ Language Standard to **ISO C++20 Standard**

![Visual Studio Project Properties](/assets/images/2026-09-30-winrt-3/coroutine-support.png)
