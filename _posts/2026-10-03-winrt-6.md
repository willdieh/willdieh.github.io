## Collections ##

So far we've only put the sample `Int32` on the UI and bound it to our C++ code using `x:Bind` with a `TextBlock` and `Click=` with a `MenuBar` in our XAML code. The `Int32` was already part of our `MainWindow.idl` runtime class definition file from the WinUI template. Remember - any data that needs to be accessed from both the XAML UI and our C++ code must be defined in an `idl` file so it can be accessed in both the XAML and C++ worlds.

What if we were designing an Address Book and wanted to have something like a `std::vector<Person>` appear on the screen? 

Because we're going to access it from both the XAML UI and C++, we'll need to define it in an `idl` file. Then we'd need to define the `Person` class or struct and put it in a `std::vector` like thing in C++, and finally add it to the XAML UI by using an appropriate UI element like a `ListView`. The `INotifyPropertyChanged` requirements from [last time]({% post_url 2026-10-02-winrt-5 %}) will still be there. We'll also have to figure out how to handle any multi-threaded update conflicts between the UI and application threads. 

If you're up for the challenge, let's get started!

### IDL Files ###

Any data crossing the XAML UI and C++ ABIs must be defined in an `idl` file. So far, we've just used the `MainWindow.idl` file which defines the `MainWindow` class as being a `Microsoft.UI.Xaml.Window` object. The default WinUI template threw in an `Int32 MyProperty` member which we made *observable* by extending the runtime class with `Microsoft.UI.Xaml.Data.INotifyPropertyChanged`. 

Going forward, we'll be writing our custom runtime classes in separate `idl` files. This allows us to separate our `MainWindow` runtime class and our individual data structure runtime classes. We'll then `import` the separate runtime class definitions in any `idl` file they're needed. 

Honestly, this seems like a purely cosmetic concession as even the Microsoft documentation says having all your runtime class definitions in a single file can improve build times and may even be necessary to avoid circular includes. I'm really tempted to just write multiple runtime class definitions in the `MainWindow.idl` file, but I guess style wins over performance.

## In with the New ##

Now we're ready to create a shiny new runtime class definition, just for our `Person` object! 

Right-click on the project in Visual Studio and select Add, New Item..., and select **View Model (C++/WinRT)**. Name it `Person` and click Add.

This will create a new `idl` file along with matching `cpp`/`h` files. Beautiful~! 

The only problem is the `idl` file contains the `[bindable]` attribute. This attribute is required for the midl compiler to generate necessary code for run-time inspection so the `{Binding}` XAML attribute can be used. Unfortunately, `{Binding}` is the *old* and *slow* way of binding data to the XAML UI. The new and improved way is to use `{x:Bind}` (like we have been doing so far). The [Microsoft Documentation](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.data.bindableattribute?view=windows-app-sdk-2.0#remarks) for `BindableAttribute Class` says it's no longer needed if we're not using `{Binding}` - so we'll just removed it. 

Let's fill out the rest of the runtime class:

**`Person.idl`**
```idl
namespace WinUIApp
{
    [default_interface]
    runtimeclass Person : Microsoft.UI.Xaml.Data.INotifyPropertyChanged
    {
        Person(String firstName, String lastName, Windows.Foundation.DateTime dateOfBirth, String phoneNumber, String email);

        String FirstName;
        String LastName;
        Windows.Foundation.DateTime DateOfBirth;
        Int32 Age{ get; };
        String PhoneNumber;
        String Email;
    }
}
```

- `Microsoft.UI.Xaml.Data.INotifyPropertyChanged` We have to inherit from this in order to send/receive data change events
- `Person(...)` Constructor takes initial values
- `Int32 Age{ get; };` Age is read-only and will be calculated based on DOB

**`Person.h`**
```c++

    struct Person : PersonT<Person, implementation::Person>

    };

```

**`Person.cpp`**
```c++
#include "pch.h"
#include "Person.h"
#if __has_include("Person.g.cpp")
#include "Person.g.cpp"
#endif

#include <chrono>   // For Age date calculations

using namespace winrt::Microsoft::UI::Xaml::Data;   // For PropertyChangedEventArgs
using namespace winrt::Windows::Foundation;         // For DateTime

namespace
{
    int32_t calculate_age(DateTime birthdate) {

        // Convert and floor both to days since SYSTEM epoch
        auto birth_days = std::chrono::floor<std::chrono::days>(winrt::clock::to_sys(birthdate));
        auto today_days = std::chrono::floor<std::chrono::days>(winrt::clock::to_sys(winrt::clock::now()));

        // Convert ONLY the birth date to year_month_day (expensive, but done once)
        std::chrono::year_month_day birth_ymd(birth_days);

        // Estimate coarse age using fast integer duration math
        int32_t age = std::chrono::floor<std::chrono::years>(today_days - birth_days).count();

        // Check if that exact anniversary falls after 'today'. 
        // If it does, the person hasn't had their birthday yet this year, so subtract 1.
        std::chrono::sys_days anniversary = birth_ymd + std::chrono::years{ age };
        if (anniversary > today_days) {
            age--;
        }

        return age;
    }
}

namespace winrt::WinUIApp::implementation
{  
    Person::Person(hstring const& firstName, hstring const& lastName, 
        DateTime const& dateOfBirth, hstring const& phoneNumber, hstring const& email)
        : m_firstName(firstName), m_lastName(lastName), m_dateOfBirth(dateOfBirth),
        m_phoneNumber(phoneNumber), m_email(email)
    {
        m_age = calculate_age(dateOfBirth);
    }

    void Person::FirstName(hstring const& value)
    {
        if (m_firstName != value)
        {
            m_firstName = value;
            RaisePropertyChanged(L"FirstName");
        }
    }

    void Person::LastName(hstring const& value)
    {
        if (m_lastName != value)
        {
            m_lastName = value;
            RaisePropertyChanged(L"LastName");
        }
    }

    void Person::DateOfBirth(Windows::Foundation::DateTime const& value)
    {
        if (m_dateOfBirth != value)
        {
            m_dateOfBirth = value;
            m_age = calculate_age(m_dateOfBirth);
            RaisePropertyChanged(L"DateOfBirth");
            RaisePropertyChanged(L"Age");
        }
    }

    void Person::PhoneNumber(hstring const& value)
    {
        if (m_phoneNumber != value)
        {
            m_phoneNumber = value;
            RaisePropertyChanged(L"PhoneNumber");
        }
    }

    void Person::Email(hstring const& value)
    {
        if (m_email != value)
        {
            m_email = value;
            RaisePropertyChanged(L"Email");
        }
    }

    hstring Person::FirstName()
    {
        return m_firstName;
    }

    hstring Person::LastName()
    {
        return m_lastName;
    }

    Windows::Foundation::DateTime Person::DateOfBirth()
    {
        return m_dateOfBirth;
    }

    int32_t Person::Age()
    {
        return m_age;
    }

    hstring Person::PhoneNumber()
    {
        return m_phoneNumber;
    }

    hstring Person::Email()
    {
        return m_email;
    }

    winrt::event_token Person::PropertyChanged(PropertyChangedEventHandler const& handler)
    {
        return m_propertyChanged.add(handler);
    }

    void Person::PropertyChanged(winrt::event_token const& token)
    {
        m_propertyChanged.remove(token);
    }

    void Person::RaisePropertyChanged(std::wstring_view propertyName)
    {
        m_propertyChanged(*this, PropertyChangedEventArgs{ propertyName });
    }
}
```

Yes, it's a lot. But it's the same stuff we did before. Let's go over it together:

- `calcuateAge` Helper function for calculating a person's age. Uses c++20 `std::chrono` functions. Anonymous namespace keeps it inside this c++ file only.
- **Getters/Setters** Here we have the old getter/setter paradigm functions. Notice the change detection to prevent unnecessary `PropertyChangedEvent` calls. Since we have to alert the UI on changes, we must **always** use the setter functions when updating member values.
- `PropertyChanged` Register/Deregister our event handlers with our local event member variable
- `RaisePropertyChanged` We call this every time a member value changes to send an update event to the UI

## MainWindow ##

Because we split our runtime class off into its own definition file, anywhere we want to use that class we must `import` it. 

Since we'll be displaying it on the main window, we need to add it to `MainWindow.idl` as part of some kind of *observable* list type. WinRT gives us something called an `IObservableVector<T>` type. This type fires off `PropertyChanged` events every time its contents change. So we'll add it to the `MainWindow` class using one of those.

**`MainWindow.idl`**
```idl
import "Person.idl";

namespace WinUIApp
{
    [default_interface]
    runtimeclass MainWindow : Microsoft.UI.Xaml.Window, Microsoft.UI.Xaml.Data.INotifyPropertyChanged
    {
        MainWindow();
        Int32 MyProperty;
        Windows.Foundation.Collections.IObservableVector<Person> People{ get; };
    }
}
```

We set People to read-only by only allowing a getter. We'd only need a setter if we wanted to completely change the underlying vector. We'll still be able to edit the individual entries in the vector because `Person` has getters and setters.

Of course we must match our `MainWindow.h`/`.cpp` files to match our `idl` definition

**`MainWindow.xaml.h`**
```c++
...
using namespace winrt::Windows::Foundation::Collections; // For IObservableVector

namespace winrt::WinUIApp::implementation
{
    struct MainWindow : MainWindowT<MainWindow>
    {
        ...
        // Getters
        IObservableVector<WinUIApp::Person> People();

    private:
        IObservableVector<WinUIApp::Person> m_people{ winrt::single_threaded_observable_vector<WinUIApp::Person>() };
        void LoadSampleData();
    };
}
...
```

**`MainWindow.xaml.cpp`**
```c++
...
namespace winrt::WinUIApp::implementation
{
    ...
    IObservableVector<WinUIApp::Person> MainWindow::People()
    {
        return m_people;
    }

    void MainWindow::LoadSampleData()
    {
        m_people.Append(winrt::make<WinUIApp::implementation::Person>(
            L"Alice",
            L"Johnson",
            winrt::clock::from_sys(std::chrono::sys_days(std::chrono::year_month_day(std::chrono::year(1995), std::chrono::June, std::chrono::day(15)))),
            L"555-0101",
            L"alice@example.com"
        ));
        m_people.Append(winrt::make<WinUIApp::implementation::Person>(
            L"Bob",
            L"Martinez",
            winrt::clock::from_sys(std::chrono::sys_days(std::chrono::year_month_day(std::chrono::year(1992), std::chrono::December, std::chrono::day(1)))),
            L"555-0102",
            L"bob@example.com"
        ));
        m_people.Append(winrt::make<WinUIApp::implementation::Person>(
            L"Carol",
            L"Nguyen",
            winrt::clock::from_sys(std::chrono::sys_days(std::chrono::year_month_day(std::chrono::year(1975), std::chrono::April, std::chrono::day(5)))),
            L"555-0103",
            L"carol@example.com"
        ));
        m_people.Append(winrt::make<WinUIApp::implementation::Person>(
            L"Dan",
            L"Okafor",
            winrt::clock::from_sys(std::chrono::sys_days(std::chrono::year_month_day(std::chrono::year(1990), std::chrono::February, std::chrono::day(20)))),
            L"555-0104",
            L"dan@example.com"
        ));
}
```

What do we have here?

- `IObservableVector` This is our *observable* vector of `Person` objects. Any time we add/remove objects from the vector, the UI will update and vice versa.
- `WinUIApp::Person` Why not just access the `Person` class directly? We can, in places where the UI does not get involved, but any time we involve the XAML UI, we must call the object *indirectly* so it fires off all the proper events that link the UI and the C++ code. We do this by referring to the object using it's Application Name (WinUIApp).
- `winrt::single_threaded_observable_vector` We initialize our `IObservableVector` with a threading model. In this case, we use the single threaded model which means only the UI thread will be updating this vector. All changes must happen through the UI or we will have threading contention. If we need to begin modifying the vector outside the setter function then we'll need to look at other options.
- `LoadSampleData` Loads sample data into our observable vector as `Person` objects

## XAML ##

Let's take a look at how we get this `Person` object to show up in the XAML UI.

**`MainWindow.xaml`**
```xaml
<?xml version="1.0" encoding="utf-8"?>
<Window
    ...
    <Grid>
        ...
        <MenuBar Grid.Row="0">
        ...
        </MenuBar>
        <ListView Grid.Row="1" ItemsSource="{x:Bind People}">
            <ListView.ItemTemplate>
                <DataTemplate x:DataType="local:Person">
                    <Grid ColumnSpacing="12">
                        <Grid.ColumnDefinitions>
                            <ColumnDefinition Width="100"/>
                            <ColumnDefinition Width="100"/>
                            <ColumnDefinition Width="300"/>
                            <ColumnDefinition Width="100"/>
                            <ColumnDefinition Width="100"/>
                            <ColumnDefinition Width="200"/>
                        </Grid.ColumnDefinitions>
                        <TextBlock Grid.Column="0" Text="{x:Bind FirstName, Mode=OneWay}"/>
                        <TextBlock Grid.Column="1" Text="{x:Bind LastName, Mode=OneWay}"/>
                        <DatePicker Grid.Column="2" Date="{x:Bind DateOfBirth, Mode=TwoWay}"/>
                        <TextBlock Grid.Column="3" Text="{x:Bind Age, Mode=OneWay}"/>
                        <TextBlock Grid.Column="4" Text="{x:Bind PhoneNumber, Mode=OneWay}"/>
                        <TextBlock Grid.Column="5" Text="{x:Bind Email, Mode=OneWay}"/>
                    </Grid>
                </DataTemplate>
            </ListView.ItemTemplate>
        </ListView>
    </Grid>
</Window>
```

- `ListView` We add a list view to the Grid at row 1 to hold our People entries. Inside the list we'll have another Grid with Textblocks for each field.
- `ItemTemplate` We have to tell XAML how to display the list of People entries
- `DataTemplate` Specifies the data type of each entry in the list
- `DataType` The name of the C++ object that holds the data
- `DatePicker` To work with `DateTime` objects we need something that understands them (or we'd have to set up another member in `Person` just to export a string DOB)
