## Collections ##

So far we've only put the sample `Int32` into a `TextBlock` on the UI and bound it to our C++ code using `x:Bind` in our XAML code. The `Int32` was already part of our `MainWindow.idl` runtime class definition file from the WinUI template. Remember - any data that needs to be accessed from both the XAML UI and our C++ code must be defined in an `idl` file so it can be accessed in both the XAML and C++ worlds.

What if we were designing an Address Book and wanted to have something like a `std::vector<Person>` appear on the screen? 

Because we're going to access it from both the XAML UI and C++, we'll need to define it in an `idl` file. Then we'd need to define the `Person` class or struct and put it in a `std::vector` like thing in C++, and finally add it to the XAML UI by using an appropriate UI element like a `ListView`. The `INotifyPropertyChanged` requirements from [last time]({% post_url 2026-10-02-winrt-5 %}) will still be there.

If you're up for the challenge, let's get started!

### IDL Files ###

Any data crossing the XAML UI and C++ ABIs must be defined in an `idl` file. So far, we've just used the `MainWindow.idl` file which defines the `MainWindow` class as being a `Microsoft.UI.Xaml.Window` object. The default WinUI template threw in an `Int32 MyProperty` member which we made *observable* by extending the runtime class with `Microsoft.UI.Xaml.Data.INotifyPropertyChanged`. 

Going forward, we'll be writing our custom runtime classes in separate `idl` files. This allows us to separate our `MainWindow` runtime class and our individual data structure runtime classes. We'll then `import` the separate runtime class definitions in any `idl` file they're needed. 

Honestly, this seems like a purely cosmetic concession as even the [Microsoft documentation](https://learn.microsoft.com/en-us/windows/apps/develop/cpp-winrt/author-apis#factoring-runtime-classes-into-midl-files-idl) says having all your runtime class definitions in a single file can improve build times and may even be necessary to avoid circular includes. I'm really tempted to just write multiple runtime class definitions in the `MainWindow.idl` file, but I guess style wins over performance.

## Out with the Old ##

First, let's remove the `Int32 MyProperty` stuff (including the `INotifyPropertyChanged`) from `MainWindow.idl`.

**`MainWindow.idl`**
```idl
namespace WinUIApp
{
    [default_interface]
    runtimeclass MainWindow : Microsoft.UI.Xaml.Window
    {
        MainWindow();
    }
}
```

Note the `[default_interface]` MIDL3 attribute. It specifies that the `MainWindow` class is the default class returned from COM when instantiated. Here's some [interesting discussion from Raymond Chen](https://devblogs.microsoft.com/oldnewthing/20240918-00/?p=110279/) on the matter. In this case it's needed because `MainWindow` doesn't contain any actual members (just a constructor) so we need to force the compiler not to default back to the `Microsoft.UI.Xaml.Window` as the default object.

Next, remove all the `MyProperty` stuff and the `INotifyPropertyChanged` event handlers from `MainWindow.xaml.h` \ `.cpp`. 

**`MainWindow.xaml.h`**
```c++
...
```

## In with the New ##

Now we're ready to create a shiny new runtime class definition, just for our `Person` object! 

Right-click on the project in Visual Studio and select Add, New Item..., and select **View Model (C++/WinRT)**. Name it `Person` and click Add.

This will create a new `idl` file along with matching `cpp`/`h` files. Beautiful~! Optionally, we could just have added a new **Midl File (.idl)**, manually typed out our runtime class definition, clicked build to allow the midl and cppwinrt compilers to autogen a matching `.cpp` \ `.h` file set in the `generated` folder, then manually imported those files into the project.

Using the **View Model (C++/WinRT)** template, the only problem is the `idl` file contains the `[bindable]` attribute. This attribute is required for the midl compiler to generate necessary code for run-time inspection so the `{Binding}` XAML attribute can be used. Unfortunately, `{Binding}` is the *old* and *slow* way of binding data to the XAML UI. The new and improved way is to use `{x:Bind}` (like we have been doing so far). The [Microsoft Documentation](https://learn.microsoft.com/en-us/windows/windows-app-sdk/api/winrt/microsoft.ui.xaml.data.bindableattribute?view=windows-app-sdk-2.0#remarks) for `BindableAttribute Class` says it's no longer needed if we're not using `{Binding}` - so we'll just remove it. 

Let's fill out the rest of the runtime class:

**`Person.idl`**
```idl
namespace WinUIApp
{
    runtimeclass Person : Microsoft.UI.Xaml.Data.INotifyPropertyChanged
    {
        Person(String firstName, String lastName, Windows.Foundation.DateTime dateOfBirth, String phoneNumber, String email);

        String FirstName;
        String LastName;
        Windows.Foundation.DateTime DateOfBirth;
        Int32 Age{ get; };
        String PhoneNumber;
        String Email;
    }
}
```

- `Microsoft.UI.Xaml.Data.INotifyPropertyChanged` We have to inherit from this in order to send/receive data change events
- `Person(...)` Declaring a constructor explicitly marks the runtime class as *activatable*. It forces the generation of an activation factory under the hood so that code can instantiate it through COM.
- `Int32 Age{ get; };` Age is read-only and will be calculated based on DOB

**`Person.h`**
```c++
#pragma once

#include "Person.g.h"

namespace winrt::WinUIApp::implementation
{
    struct Person : PersonT<Person>
    {
        Person(winrt::hstring const& firstName, winrt::hstring const& lastName,
            Windows::Foundation::DateTime const& dateOfBirth,
            winrt::hstring const& phoneNumber, winrt::hstring const& email);

        // Setters
        void FirstName(winrt::hstring const& value);
        void LastName(winrt::hstring const& value);
        void DateOfBirth(Windows::Foundation::DateTime const& value);
        void PhoneNumber(winrt::hstring const& value);
        void Email(winrt::hstring const& value);

        // Getters
        winrt::hstring FirstName();
        winrt::hstring LastName();
        Windows::Foundation::DateTime DateOfBirth();
        int32_t Age();              // Read-Only (No Setter)
        winrt::hstring PhoneNumber();
        winrt::hstring Email();

        // INotifyPropertyChanged event handler registration/deregistration
        winrt::event_token PropertyChanged(Microsoft::UI::Xaml::Data::PropertyChangedEventHandler const& handler);
        void PropertyChanged(winrt::event_token const& token);

    private:
        // Sends a property changed event
        void RaisePropertyChanged(std::wstring_view propertyName);

        winrt::hstring m_firstName;
        winrt::hstring m_lastName;
        Windows::Foundation::DateTime m_dateOfBirth;
        int32_t m_age;
        winrt::hstring m_phoneNumber;
        winrt::hstring m_email;

        // Event for propertyChanged
        winrt::event<Microsoft::UI::Xaml::Data::PropertyChangedEventHandler> m_propertyChanged;
    };
}

namespace winrt::WinUIApp::factory_implementation
{
    struct Person : PersonT<Person, implementation::Person>
    {
    };
}
```

**`Person.cpp`**
```c++
#include "pch.h"
#include "Person.h"
#if __has_include("Person.g.cpp")
#include "Person.g.cpp"
#endif

#include <chrono>   // For Age date calculations

using namespace winrt::Microsoft::UI::Xaml::Data;   // For PropertyChangedEventArgs
using namespace winrt::Windows::Foundation;         // For DateTime

namespace
{
    int32_t CalculateAge(DateTime birthdate)
    {
        // Convert both timestamps to calendar dates (UTC)
        std::chrono::year_month_day birth{ std::chrono::floor<std::chrono::days>(winrt::clock::to_sys(birthdate)) };
        std::chrono::year_month_day today{ std::chrono::floor<std::chrono::days>(winrt::clock::to_sys(winrt::clock::now())) };

        // Whole years between the two calendar years...
        int32_t age = static_cast<int32_t>(today.year()) - static_cast<int32_t>(birth.year());

        // ...minus one if this year's birthday hasn't happened yet
        if (today.month() < birth.month() ||
            (today.month() == birth.month() && today.day() < birth.day()))
        {
            --age;
        }

        return age;
    }
}

namespace winrt::WinUIApp::implementation
{  
    Person::Person(winrt::hstring const& firstName, winrt::hstring const& lastName, 
        DateTime const& dateOfBirth, winrt::hstring const& phoneNumber, winrt::hstring const& email)
        : m_firstName(firstName), m_lastName(lastName), m_dateOfBirth(dateOfBirth),
        m_phoneNumber(phoneNumber), m_email(email)
    {
        m_age = CalculateAge(dateOfBirth);
    }

    void Person::FirstName(winrt::hstring const& value)
    {
        if (m_firstName != value)
        {
            m_firstName = value;
            RaisePropertyChanged(L"FirstName");
        }
    }

    void Person::LastName(winrt::hstring const& value)
    {
        if (m_lastName != value)
        {
            m_lastName = value;
            RaisePropertyChanged(L"LastName");
        }
    }

    void Person::DateOfBirth(Windows::Foundation::DateTime const& value)
    {
        if (m_dateOfBirth != value)
        {
            m_dateOfBirth = value;
            m_age = CalculateAge(m_dateOfBirth);
            RaisePropertyChanged(L"DateOfBirth");
            RaisePropertyChanged(L"Age");
        }
    }

    void Person::PhoneNumber(winrt::hstring const& value)
    {
        if (m_phoneNumber != value)
        {
            m_phoneNumber = value;
            RaisePropertyChanged(L"PhoneNumber");
        }
    }

    void Person::Email(winrt::hstring const& value)
    {
        if (m_email != value)
        {
            m_email = value;
            RaisePropertyChanged(L"Email");
        }
    }

    winrt::hstring Person::FirstName()
    {
        return m_firstName;
    }

    winrt::hstring Person::LastName()
    {
        return m_lastName;
    }

    Windows::Foundation::DateTime Person::DateOfBirth()
    {
        return m_dateOfBirth;
    }

    int32_t Person::Age()
    {
        return m_age;
    }

    winrt::hstring Person::PhoneNumber()
    {
        return m_phoneNumber;
    }

    winrt::hstring Person::Email()
    {
        return m_email;
    }

    winrt::event_token Person::PropertyChanged(PropertyChangedEventHandler const& handler)
    {
        return m_propertyChanged.add(handler);
    }

    void Person::PropertyChanged(winrt::event_token const& token)
    {
        m_propertyChanged.remove(token);
    }

    void Person::RaisePropertyChanged(std::wstring_view propertyName)
    {
        m_propertyChanged(*this, PropertyChangedEventArgs{ propertyName });
    }
}
```

Yes, it's a lot. But it's the same stuff we did before. Let's go over it together:

- `CalcuateAge` Helper function for calculating a person's age. Uses c++20 `std::chrono` functions. Anonymous namespace keeps it inside this c++ file only.
- **Getters/Setters** Here we have the old getter/setter paradigm functions. Notice the change detection to prevent unnecessary `PropertyChangedEvent` calls. Since we have to alert the UI on changes, we must **always** use the setter functions when updating member values.
- `PropertyChanged` Register/Deregister our event handlers with our local event member variable
- `RaisePropertyChanged` We call this every time a member value changes to send an update event to the UI
- `winrt::hstring` This is the native WinRT string type. We could store the fields in C++ `std::wstring` but our getters would have to always have to convert them to into `winrt::hstring`.

## MainWindow ##

Because we split our runtime class off into its own definition file, anywhere we want to use that class we must `import` it. 

Since we'll be displaying it on the main window, we need to add it to `MainWindow.idl` as part of some kind of *observable* list type. WinRT gives us something called an `IObservableVector<T>` type. This type fires off `PropertyChanged` events every time its contents change. So we'll add it to the `MainWindow` class using one of those.

**`MainWindow.idl`**
```idl
import "Person.idl";

namespace WinUIApp
{
    [default_interface]
    runtimeclass MainWindow : Microsoft.UI.Xaml.Window
    {
        MainWindow();

        Windows.Foundation.Collections.IObservableVector<Person> People{ get; };
    }
}
```

We set People to read-only by only allowing a getter. We'd only need a setter if we wanted to completely change the underlying vector. We'll still be able to edit the individual entries in the vector because `Person` has getters and setters.

Of course we must match our `MainWindow.h`/`.cpp` files to match our `idl` definition

**`MainWindow.xaml.h`**
```c++
...
using namespace winrt::Windows::Foundation::Collections; // For IObservableVector

namespace winrt::WinUIApp::implementation
{
    struct MainWindow : MainWindowT<MainWindow>
    {
        MainWindow()
        {
            // Xaml objects should not call InitializeComponent during construction.
            // See https://github.com/microsoft/cppwinrt/tree/master/nuget#initializecomponent
            LoadSampleData();
        }
        ...
        // Getters
        IObservableVector<WinUIApp::Person> People();

    private:
        IObservableVector<WinUIApp::Person> m_people{ winrt::single_threaded_observable_vector<WinUIApp::Person>() };
        void LoadSampleData();
    };
}
...
```

**`MainWindow.xaml.cpp`**
```c++
...
#include "Person.h" // For implementation::Person
#include <chrono>   // For std::chrono
...
namespace winrt::WinUIApp::implementation
{
    ...
    IObservableVector<WinUIApp::Person> MainWindow::People()
    {
        return m_people;
    }

    void MainWindow::LoadSampleData()
    {
        m_people.Append(WinUIApp::Person{
            L"Alice",
            L"Johnson",
            winrt::clock::from_sys(std::chrono::sys_days(std::chrono::year_month_day(std::chrono::year(1995), std::chrono::June, std::chrono::day(15)))),
            L"555-0101",
            L"alice@example.com"
        });
        m_people.Append(WinUIApp::Person{
            L"Bob",
            L"Martinez",
            winrt::clock::from_sys(std::chrono::sys_days(std::chrono::year_month_day(std::chrono::year(1992), std::chrono::December, std::chrono::day(1)))),
            L"555-0102",
            L"bob@example.com"
        });
        m_people.Append(WinUIApp::Person{
            L"Carol",
            L"Nguyen",
            winrt::clock::from_sys(std::chrono::sys_days(std::chrono::year_month_day(std::chrono::year(1975), std::chrono::April, std::chrono::day(5)))),
            L"555-0103",
            L"carol@example.com"
        });
        m_people.Append(WinUIApp::Person{
            L"Dan",
            L"Okafor",
            winrt::clock::from_sys(std::chrono::sys_days(std::chrono::year_month_day(std::chrono::year(1990), std::chrono::February, std::chrono::day(20)))),
            L"555-0104",
            L"dan@example.com"
        });
    }
}
```

What do we have here?

- `IObservableVector` This is our *observable* vector of `Person` objects. Any time we add/remove objects from the vector, the UI will update and vice versa.
- `winrt::single_threaded_observable_vector` We initialize our `IObservableVector` with a threading model. In this case, we use the single threaded model which is fine if only the UI thread will be updating this vector. 
- `LoadSampleData` Loads sample data into our observable vector as `Person` objects
- `WinUIApp::Person` Why not just access the `Person` class directly? We can, in places where the UI does not get involved, but any time we involve the XAML UI, we must call the object *indirectly* so it fires off all the proper events that link the UI and the C++ code. We do this by referring to the object using its *projection* (`WinUIApp::Person`) instead of its C++ *implementation* (`WinUIApp::implementation::Person`). Calling the *projection* retrieves the object via COM. Calling the *implementation* accesses the C++ variable directly.

Here's a snappy little image that helps illustrate *projected* vs *implementation* for a runtime class named `MyProject::MyRuntimeClass`. Note how the *projected* object uses a pointer (COM) to retrieve the *impelementation* object:

![Projected vs Implementation](/assets/images/2026-10-03-winrt-6/projected-vs-implementation.png)

Before cpp/winrt 2.0, we would have had to call `winrt::make<WinUIApp::implementation::Person>({...})` to get the projected type in our code. Version 2.0 brought something called [Uniform Construction](https://learn.microsoft.com/en-us/windows/apps/develop/cpp-winrt/author-apis#opt-in-to-uniform-construction-and-direct-implementation-access) which allows us to use the projected object just like a normal C++ type. So we can do something like `auto bob = WinUIApp::Person{...}` and no longer need to use `winrt::make<T>`. It's just *really* important to remember to use the *projected* namespace `WinUIApp::Person` and not the *implementation* namespace `WinUIApp::implementation::Person` because we need all that COM magic to happen behind the scenes.

## XAML ##

Let's take a look at how we get this `Person` object to show up in the XAML UI.

**`MainWindow.xaml`**
```xaml
<?xml version="1.0" encoding="utf-8"?>
<Window
    ...
    <Grid>
        ...
        <MenuBar Grid.Row="0">
        ...
        </MenuBar>
        <ListView Grid.Row="1" ItemsSource="{x:Bind People}">
            <ListView.ItemTemplate>
                <DataTemplate x:DataType="local:Person">
                    <Grid ColumnSpacing="12">
                        <Grid.ColumnDefinitions>
                            <ColumnDefinition Width="100"/>
                            <ColumnDefinition Width="100"/>
                            <ColumnDefinition Width="300"/>
                            <ColumnDefinition Width="100"/>
                            <ColumnDefinition Width="100"/>
                            <ColumnDefinition Width="200"/>
                        </Grid.ColumnDefinitions>
                        <TextBlock Grid.Column="0" Text="{x:Bind FirstName, Mode=OneWay}"/>
                        <TextBlock Grid.Column="1" Text="{x:Bind LastName, Mode=OneWay}"/>
                        <DatePicker Grid.Column="2" Date="{x:Bind DateOfBirth, Mode=TwoWay}"/>
                        <TextBlock Grid.Column="3" Text="{x:Bind Age, Mode=OneWay}"/>
                        <TextBlock Grid.Column="4" Text="{x:Bind PhoneNumber, Mode=OneWay}"/>
                        <TextBlock Grid.Column="5" Text="{x:Bind Email, Mode=OneWay}"/>
                    </Grid>
                </DataTemplate>
            </ListView.ItemTemplate>
        </ListView>
    </Grid>
</Window>
```

- `ListView` We add a list view to the Grid at row 1 to hold our People entries. Inside the list we'll have another Grid with Textblocks for each field.
- `ItemTemplate` We have to tell XAML how to display the list of People entries
- `DataTemplate` Specifies the data type of each entry in the list
- `DataType="local:Person"` The name of the C++ object that holds the data. `local` is defined in `App.xaml` as `xmlns:local="using:WinUIApp"` 
- `DatePicker` To work with `DateTime` objects we need something that understands them (or we'd have to set up another member in `Person` just to export a string DOB)
